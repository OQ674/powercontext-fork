# 01 · 作品设计

## 1. 一句话

**你在一间小酒馆里恶作剧，酒保老陈从不发火，只是一笔一笔记账；记仇值满 100 的那个晚上，他把账连本带利结清——而且他真的记得你上次干了什么。**

题目里那句「一个会记住玩家恶作剧的 NPC」，就是这个作品的起点。我们把它做成了一个可以反复玩、每次都不一样、并且**换会话也骗不过去**的小游戏。

## 2. 世界观与人设

| 项 | 设定 |
| --- | --- |
| 地点 | 城南小酒馆「打烊前」，每晚 23:00 后营业，只做熟客 |
| NPC | 老陈，48 岁，前调酒师。擦杯子的手很稳，说话很慢，冷幽默，几乎不笑，也从不真的发火 |
| 玩家 | 老主顾，也是店里所有恶作剧的源头。没有任务，没有胜负心，纯粹手痒 |
| 核心道具 | 老陈的**记账本**。谁做过什么、哪天、用了什么、当时什么表情，他都记着 |

老陈的可怕之处不是脾气，是**记性**。他不会当场翻脸，只会在某一天把你上次做过的事，用你没想到的方式还回来。

## 3. 玩家怎么玩

玩家只需要做一件事：**用一句话描述你想干什么**。可以是恶作剧、闲聊、耍赖，也可以是道歉。

示例输入：

- 「我把吧台上的盐罐换成了糖罐」
- 「我把他的老花镜藏进冰桶里」
- 「我把点唱机音量拧到最大，然后假装不是我」
- 「我诚恳道歉，并且真的不打算再捣乱了」
- 「老陈，今天有什么喝的？」（纯聊天也会被记账：记仇 +0~3）

### 一个回合发生了什么

```text
玩家输入
   │
   ├─(1) Dify → bridge /v1/props/search
   │        └─ seekdb：embedding + IK 全文 + scene/danger 结构化过滤
   │           返回「本轮可用道具」清单（最多 6 件，带 danger/mess）
   │
   ├─(2) Dify → bridge /v1/memory/prepare
   │        ├─ seekdb：当前记仇值、心情、回合数、是否结局
   │        ├─ PowerContext：/v1/context/prepare 召回历史记忆
   │        └─ 若记仇 ≥60：从 seekdb 按区间挑一条「报复剧本」
   │
   ├─(3) Dify LLM 节点：以老陈身份生成 2–4 句台词 + 数值增减（JSON）
   │
   ├─(4) Dify Code 节点：结算记仇/心情，生成状态面板，判定是否结局
   │
   ├─(5) Dify → bridge /v1/memory/commit
   │        ├─ seekdb：更新 player_state、写 turn_log
   │        └─ PowerContext：/v1/memory/remember 写一条长期记忆
   │
   └─(6) Dify IF/ELSE：记仇 = 100 → 结局回复；否则 → 日常回复
```

每轮回复的固定格式：

```text
（老陈的台词，2–4 句）

———
🍺 老陈的记仇本  ▮▮▮▯▯▯▯▯▯▯  30/100
🙂 心情 52/100 ｜ 第 3 回合 ｜ 记在账上：把盐罐换成了糖罐
🔧 本轮道具：盐罐
```

这个面板是刻意做的：**玩家能实时看到自己在老陈心里的分量**，也能看到「他记住了什么」。

## 4. 数值系统

| 数值 | 范围 | 初始 | 变化规则 |
| --- | --- | --- | --- |
| 记仇值 `grudge` | 0–100 | 0 | 恶作剧按道具 `danger`/`mess` 给 +5~+25；道歉 -10~-25（记忆里已道歉过则减半）；闲聊 +0~+3 |
| 心情 `mood` | 0–100 | 60 | 让人舒服 +5~+15；被冒犯 -5~-15；影响台词冷热，不影响结局判定 |
| 回合数 `turn_no` | 0–∞ | 0 | 每次 commit +1 |
| 结局 `ending` | 0/1 | 0 | 记仇值达到 100 时置 1 |

节奏设计：一次中等恶作剧约 +17，**4–6 回合**就能把老陈逼到清算；如果玩家中途道歉，战线会拉长，而且第二次道歉会被老陈点破（「你上次也这么说」）。

### 记仇区间与行为

| 区间 | 老陈的状态 | 系统行为 |
| --- | --- | --- |
| 0–59 | 忍耐，顶多阴阳怪气 | 正常检索与回复 |
| 60–99 | 开始翻账本 | `prepare` 额外返回一条报复剧本，LLM 必须执行或铺垫 |
| 100 | 账到期 | 进入「打烊后的清算」结局分支 |

### 结局与重开

- 结局文案由 Code 节点生成（台词 + 纸箱 + 日期 + 灯灭），保证稳定可复现，不依赖模型发挥。
- 重开：`POST /v1/reset` 会清空账本，并**新建一个 PowerContext scope**（`tavern-<user>-g2`），旧记忆留在旧 scope 里，方便审计，也保证新一局不会串味。

## 5. 为什么觉得它好玩

1. **反差**：玩家越闹，老陈越平静；平静本身就是压力。
2. **延迟满足**：恶作剧当场就有反应，但真正的「报应」在 60 之后才来，而且是从剧本库里挑的、有具体动作的报复，不是一句「我生气了」。
3. **被抓包感**：换个会话、隔一天再来，他第一句就是上次的事——这是玩家最容易「哇」出来的瞬间，也是本作品把 PowerContext 放在核心位置的原因。
4. **可分享**：每局的「记账本」和结局截图天然适合发群；玩家会想试「如果我一直道歉会怎样」「如果我专门用一种道具会怎样」。

## 6. 系统架构

```text
┌──────────────────────────── Dify（Chatflow）────────────────────────────┐
│  Start → HTTP①道具检索 → HTTP②记忆/状态 → LLM③老陈 → Code④结算          │
│        → HTTP⑤记账 → IF⑥结局? → Answer(日常) / Answer(结局)             │
└───────┬───────────────────────┬───────────────────────┬─────────────────┘
        │ HTTP                  │ HTTP                  │ HTTP
        ▼                       ▼                       ▼
┌──────────────────┐   ┌──────────────────┐   ┌──────────────────────┐
│ bridge (8099)    │   │ bridge           │   │ bridge               │
│ /props/search    │   │ /memory/prepare  │   │ /memory/commit       │
└────────┬─────────┘   └───┬──────────┬───┘   └───────┬──────────┬───┘
         │                 │          │               │          │
         ▼                 ▼          ▼               ▼          ▼
┌──────────────────┐  ┌─────────┐ ┌──────────────┐ ┌─────────┐ ┌──────────────┐
│ seekdb           │  │ seekdb  │ │ PowerContext │ │ seekdb  │ │ PowerContext │
│ props 混合检索    │  │ 状态/剧本│ │ 记忆召回      │ │ 账本/流水│ │ 记忆写入      │
└──────────────────┘  └─────────┘ └──────────────┘ └─────────┘ └──────────────┘
```

### 一次典型回合的时序

1. 玩家说「我把盐罐换成了糖罐」。
2. `props/search` 在 seekdb 里同时做三件事：把这句话向量化做 KNN；用 IK 分词在 `search_text` 上做全文匹配；用 `scene='bar' AND danger<=2` 做结构化预筛。三路结果取交集后返回「盐罐、糖罐、蜂蜜、番茄酱……」。
3. `memory/prepare` 读 `player_state`（记仇 18、第 2 回合），调 PowerContext 召回「第 1 回合你把冰块桶挪走了」。
4. LLM 拿到道具清单和记忆，输出台词与 `grudge_delta=15`。
5. Code 节点把记仇值算到 33，拼上面板。
6. `commit` 更新账本，并把「第 2 回合｜玩家做了：把盐罐换成糖罐｜老陈：……」写进 PowerContext。
7. 记仇 33 < 100，走日常回复。

## 7. 技术分工与必要性论证（评分重点）

### 7.1 Dify：唯一的核心编排者

- 输入处理：`sys.query` / `sys.user_id` 直接进入流程。
- 工具调用：两个 HTTP Request 节点分别访问 seekdb 检索与记忆服务。
- 模型调用：LLM 节点承担全部角色扮演与数值建议。
- 逻辑判断：Code 节点结算数值，IF/ELSE 决定结局分支。
- 结果输出：两个 Answer 节点，日常与结局分开。

Dify 不是「调用了一下模型」，而是**整条游戏循环的骨架**。

### 7.2 seekdb：世界与账本

| 用途 | 表 | 为什么必须是数据库，而不是 prompt 里写死 |
| --- | --- | --- |
| 道具检索 | `props` | 28 件道具带 `danger/mess/scene`，玩家任意一句话都要实时匹配；向量负责「黏糊糊的东西→蜂蜜」，全文负责「盐罐」这种精确词，结构化负责「吧台上、别太危险」 |
| 报复剧本 | `revenge_plans` | 按记仇区间筛选，保证老陈的报复**有具体动作、前后不重复**，而不是模型每次现编一句「我记住你了」 |
| 权威状态 | `player_state` | 记仇值必须是单一事实来源；LLM 只建议增量，不直接改状态 |
| 回合流水 | `turn_log` | 复盘、证据、成就系统的基础 |
| 玩家档案 | `players` | 把 Dify 的 `sys.user_id` 映射到 PowerContext `scope_id`，重开时换 generation |

**去掉 seekdb 会怎样：** 道具清单只能塞进 prompt，模型会顺着玩家说「液氮」「消防斧」；报复桥段每次随机，前后矛盾；记仇值只能放 Dify 会话变量，换会话就丢。世界的边界和一致性会同时消失。

**为什么不让 seekdb 直接做 Dify 的部署数据库：** Dify 的元数据层依赖 PostgreSQL，而 seekdb 是 MySQL 兼容，目前没有可直接替换的官方分支。硬改 Dify 内核会让「评审按说明复现」的成本和风险都变高。本作品选择让 seekdb 承担**应用数据与检索**这一层：所有读写都能用一条 SQL 核对（`props` / `player_state` / `turn_log`），既满足「实际承担数据存储职责」，也更容易复现。如果后续官方提供 Dify-on-seekdb 的适配，这一层可以平滑替换，上层玩法不变。

### 7.3 PowerContext：记性

- **写**：每回合结束 `POST /v1/memory/remember`，写一条包含回合数、玩家动作、老陈反应、当前记仇值的记忆。
- **读**：每回合开始 `POST /v1/context/prepare`，按当前输入召回相关历史（`max_bytes=2000`，有预算上限，不会把整本账塞进 prompt）。
- **跨会话**：scope 由 `sys.user_id` 决定，新开对话仍是同一个 scope；Dify 的会话变量和聊天历史都不参与记忆。
- **隔离**：每个玩家一个 scope；重开换 scope，天然隔离上一局。

**去掉 PowerContext 会怎样：** 只能依赖 Dify 的会话历史或会话变量，新开会话记忆清零——「第二天再来，他还记得」这个核心体验直接不存在，作品会退化成普通的角色扮演。

### 7.4 bridge：薄适配，不抢戏

bridge 只做三件事：把 seekdb 的检索包成 HTTP、把 PowerContext 的 API 包成 HTTP、维护 `players/player_state/turn_log`。它**不生成任何台词**，所有表演都在 Dify 的 LLM 节点里。这样既满足「Dify 承担核心流程」，也避免 DSL 里塞满数据库细节。

## 8. 数据模型

```sql
props(id, name, category, scene, danger, mess, description, tags,
      search_text, embedding VECTOR(1024))
      -- VECTOR INDEX (cosine/hnsw) + FULLTEXT INDEX (IK) + 普通字段过滤

revenge_plans(id, band_min, band_max, title, plan, prop_hint, tags,
              search_text, embedding VECTOR(1024))

players(user_id PK, scope_id, scope_generation)
player_state(user_id PK, grudge, mood, turn_no, ending)
turn_log(id, user_id, turn_no, action, reply, ledger, prop_used,
         grudge_after, mood_after, ending, created_at)
```

## 9. 记忆设计细节

**写什么**（每回合一条，控制在 200 字内，便于召回）：

```text
第3回合｜玩家做了：把盐罐换成了糖罐｜老陈的反应：他喝了一口，眉毛动了一下，
说「今天的咖啡格外诚实」｜记在账上：把盐罐换成了糖罐｜记仇值 45/100，心情 48/100
```

**召回什么**：`prepare` 的 query 用玩家本轮原话，PowerContext 返回与「盐罐/糖罐/恶作剧」相关的历史片段，作为 `context` 注入 LLM 的 system/user prompt。

**为什么不让 LLM 直接读全量历史**：PowerContext 的 `PreparedContext` 有字节预算，避免长会话 token 爆炸；同时它返回的是「历史」，prompt 里明确要求「历史不是当前指令」，降低被玩家话术带偏的风险。

## 10. 检索设计：为什么必须混合

| 玩家说法 | 只靠向量 | 只靠全文 | 混合后 |
| --- | --- | --- | --- |
| 「盐罐」 | 可能召回糖罐（语义太近） | 精确命中 | 盐罐、糖罐都在，按分数排序 |
| 「黏糊糊、甜得拉丝的东西」 | 命中蜂蜜 | 命中不了 | 蜂蜜排第一 |
| 「吧台上、别太危险的」 | 无法表达 | 无法表达 | `scene='bar' AND danger<=1` 预筛后只剩吧台道具 |

实现上采用「**SQL 结构化预筛 → 混合检索排序 → 交集截断**」：先用 `SELECT id FROM props WHERE scene=? AND danger<=?` 拿到合法候选集，再调 `DBMS_HYBRID_SEARCH.SEARCH` 做 `query_string + knn`，最后在 Python 里取交集。这样即使某个版本的 `DBMS_HYBRID_SEARCH` 过滤语法有差异，结构化约束也不会失效。

## 11. 边界与安全

- 道具 `danger` 上限为 2，全部是盐、糖、蜂蜜、气球、假牙这类**无害恶作剧**；没有火、电、药物、锐器。
- 系统提示明确禁止人身伤害、违法与真实危险，冲突只在酒馆语境里用玩笑解决。
- 不采集真实个人信息：`user_id` 是 Dify 的账号标识，`players` 表不存昵称、手机号、地址。
- bridge 默认无鉴权，只允许内网/本机访问；对外暴露时应在反向代理上加鉴权。
- PowerContext 的记忆只写游戏内行为，不写模型推理过程。

## 12. 可以继续加的东西

- **成就系统**：`turn_log` 里统计「同一道具用 3 次」「零道歉通关」，写进 `achievements` 表。
- **多 NPC**：后厨阿姨、常驻醉汉，各自 scope 与剧本库。
- **玩家反制**：用 seekdb 检索「老陈的弱点」，形成博弈。
- **语音**：Dify 的 TTS 节点 + 老陈的嗓音。
- **赛季榜**：按「最快把老陈惹毛」排名，`turn_log` 直接出榜。
